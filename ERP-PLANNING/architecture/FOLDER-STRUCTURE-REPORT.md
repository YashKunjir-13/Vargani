**Scope:** full audit of the pnpm/Nx monorepo (`apps/api`, `apps/worker`, `apps/scheduler`, `apps/mobile`, `packages/backend-*`, `infrastructure/`, root tooling) as it exists on disk today, cross-checked against `PROJECT-CONTEXT.md`, `ARCHITECTURE-BIBLE.md`, `BUSINESS-RULES.md`, and the backend spec. Roadmap task `P0-002`. Addenda below cover `P0-003` (the follow-up pass that closed several of this report's own findings), `P1-000` (the RBAC decision needed before Phase 1 can start), and `P0-004` (a properly-configured check across `apps/`/`packages/` that fixed the rootDir bug for real).

## Addendum (P0-004) — apps/packages configuration check

User asked to verify `apps/` and `packages/` are properly configured. Three real issues found and fixed, all verified with actual command output:

**1. Phantom dependency in `packages/backend-testing`.** Its three spec files import `@pauti-pustak/backend-config`, `@pauti-pustak/backend-contracts`, and `@pauti-pustak/backend-security`, but none were declared in its `package.json` — the same class of bug as the `@nestjs/core` gap found earlier in `backend-security`. Fixed by adding all three as `workspace:*` dependencies (the convention already used by `apps/api`). Note: this doesn't affect `jest` test execution itself — `jest.config.js` has its own `moduleNameMapper` that resolves `@pauti-pustak/*` straight to each package's `src/index.ts`, bypassing `node_modules` entirely — but it does matter for pnpm's install graph, Nx's task ordering, and IDE type resolution.

**2. The `rootDir` build bug (documented as unfixed in the P0-003 addendum) is now actually fixed**, via TypeScript project references — the standard solution for exactly this situation (a `tsc`-per-package monorepo where an app needs to type-check against a sibling package's source, not a pre-built `dist/`). Added `"composite": true` to the 6 leaf packages (`backend-config`, `backend-contracts`, `backend-database`, `backend-observability`, `backend-security`, `backend-shared-kernel`) and a `"references"` array (matching each project's actual `package.json` dependencies) to `apps/api`, `apps/worker`, `apps/scheduler`, and `packages/backend-testing`. Verified for real, not assumed: cleared every `.tsbuildinfo` and `dist/` first, then ran `tsc -b` fresh —
- `tsc -b apps/api` → builds all 6 referenced packages in correct dependency order, then `apps/api` itself, exit 0, correct flat output (`apps/api/dist/main.js`, `apps/api/dist/<service>/*.js` — not the broken nested `dist/apps/api/apps/api/...` shape seen before).
- `tsc -b apps/worker apps/scheduler` → exit 0, same correct flat output.
- `tsc -b packages/backend-testing` → exit 0.
- Re-running any of the above immediately after → exit 0, no rebuild (incremental cache working correctly).

  Worth noting precisely what this bug did and didn't block, since the earlier addendum's phrasing was broader than warranted: `pnpm dev:api` (via `tsx watch`) and `pnpm test` (via `jest`+`ts-jest` against root `tsconfig.base.json`, which has no `rootDir` restriction) were **never actually blocked** by this — only the production `build` path (and a standalone `tsc --noEmit -p <app>/tsconfig.json`) was. Still worth fixing properly rather than leaving as a known gap, since `build` is exactly what CI and deployment depend on.

**3. Stray compiled output removed from source directories.** 22 `.js`/`.d.ts`/`.js.map` files had leaked directly into `src/` (not `dist/`) in `backend-config`, `backend-contracts`, and `backend-security` — leftovers from some earlier non-`-b` `tsc` invocation. These were untracked but would have polluted the repo the moment anyone ran `git add .`, since `.gitignore` excluded `dist/` and `*.tsbuildinfo` but had no rule for compiled output landing in `src/`. Deleted the stray files and added a `.gitignore` rule (`apps/*/src/**/*.js`, `packages/*/src/**/*.js`, etc., explicitly not touching `packages/backend-database/src/generated/`, which has its own dedicated rule) to stop it recurring.

**Everything else checked out clean:** every package/app's `tsconfig.json` extends `tsconfig.base.json` consistently; `pnpm-workspace.yaml` and `tsconfig.base.json`'s `paths` cover all 7 packages; `project.json` (Nx) present and consistent for all 3 backend apps; every other package's declared dependencies were a superset of (or exactly matched) what's actually imported — no other phantom dependencies found; `apps/mobile/pubspec.lock` now exists and confirms `intl` resolved to exactly `0.20.2` as required (the earlier version-conflict fix took effect — `flutter pub get` has succeeded since).

## Addendum (P1-000) — RBAC model decision, resolved

This report's P0-003 addendum flagged a real conflict: `backend-security` shipped with a hardcoded 6-value `UserRole` enum wired into `TenantGuard`/`EventGuard`/JWT claims, while the spec (and the Prisma schema modeled in P0-003) calls for per-organization custom roles (`OrganizationRole`/`Permission`/`RolePermission`). **Decision: build on the spec's custom-role model.** Changes made, all verified with `tsc --noEmit` (clean on both `packages/backend-security` and `packages/backend-testing`):

- `auth.interfaces.ts` rewritten: `JwtAccessTokenPayload` now matches the Auth module spec's exact claim list (`sub`, `platformRole`, `membershipId`, `organizationId`, `roleId`, `tokenVersion`, `sessionId`) instead of an ad-hoc `roles`/`permissions` array. Permission codes are deliberately *not* embedded in the token — they resolve server-side from `roleId` per request, so a permission change takes effect without waiting for token expiry.
- `rbac.guards.ts` rewritten: `TenantGuard`/`EventGuard` check `platformRole === SUPER_ADMIN` and `organizationId` instead of `roles.includes(UserRole.SUPER_ADMIN)`.
- New `permission.guard.ts`: a `PermissionGuard` + `@RequirePermission(code)` decorator implementing FR57 ("every protected controller action declares permission metadata"). No Owner/Super-Admin bypass by design — FR54 only protects the Owner *role* from having its own permissions revoked, it doesn't grant an implicit bypass elsewhere.
- Added `@nestjs/core` to `backend-security`'s `package.json` (needed for `Reflector`, wasn't previously a declared dependency) — **the lockfile has not been regenerated**, since this environment has no working `pnpm`; run `pnpm install` before relying on this.
- Updated the one real consumer that would have broken: `packages/backend-testing/src/tenant-isolation.spec.ts`, now written against the new `AuthenticatedUser` shape (not executed here — no working `pnpm`/`jest`).
- Deleted three stale, now-inconsistent `.d.ts` files that were sitting directly in `backend-security/src/` (build artifacts mirroring the *old* interfaces, which is more of a problem right after a source rewrite than before). Note: `backend-config/src/` and `backend-contracts/src/` have the same stray-`.d.ts`-in-`src/` pattern, untouched here since they weren't part of this change and aren't stale relative to their own source — worth a cleanup pass separately.

**Not done — genuine Phase 1 work, not a RBAC-model-selection task:** the actual resolution step that populates `request.user.permissions` from `roleId` (a `RolePermission`/`Permission` DB lookup, likely cached) doesn't exist yet. The guard/decorator mechanism is correct and ready; nothing calls it with real data yet.

## Addendum (P0-003) — domain modeling and setup-gap closure

Everything below was verified with real command output in this environment (Node v22.16.0 and the repo's local `node_modules/.bin/prisma` 6.19.3 and `tsc` were available even though `flutter`/`dart`/`melos`/`pnpm` were not) — nothing here is a claimed-but-unverified change.

**1. Prisma domain schema modeled and verified.** `packages/backend-database/prisma/schema.prisma` grew from 4 generic infra models to ~38 models covering every module in the spec: Users/Auth (`User`, `AuthIdentity`, `OtpChallenge`, `RefreshSession`), Donor Profiles (`DonorProfile`, `DonorAlias`, `DonorMergeLog`), Tenant/Roles (`Organization`, `OrganizationMembership`, `OrganizationRole`, `Permission`, `RolePermission`), `Event`, Volunteers (`Volunteer`, `VolunteerAssignment`), `ContributorAccount`, Receipt Books (`ReceiptBook`, `ReceiptCounter`, `ReceiptNumberReservation`), Bills (`ContributionBill`, `ContributionBillLine`, `BillGenerationJob`), Collections (`CollectionRecord`, `CollectionAllocation`, `CollectorSettlement`), `ContributionRecord`, `Receipt`, `Vendor`, Expense Policy (`ExpenseApprovalPolicy`, `ExpenseApprovalPolicyBand`, `ExpenseApprovalPolicySnapshot`), Expenses (`Expense`, `ExpenseApproval`, `ExpensePayment`, `ExpenseAttachment`), Finance (`FinancialAccount`, `InternalTransfer`, `LedgerTransaction`, `LedgerEntry`), Public Transparency (`PublicEventPage`, `PublicFinancialSnapshot`), `AuditLog`, `PlatformAdminCase`, Documents (`DocumentAsset`, `RedactedDocument`).
   - Verified: `prisma validate` → *"is valid"*; `prisma generate` → *"Generated Prisma Client (v6.19.3)"* with zero errors.
   - Relations (`@relation`) were only added where the source spec text showed them explicitly, or where one side already declared a back-relation array forcing the other; every other cross-model reference (e.g. `organizationId`, `eventId`, `createdByUserId`, `donorProfileId`) is an intentional scalar UUID column with no FK, matching the spec's own "no cross-service FK" convention for fields owned by a different bounded context. A few fields in the source PDF were column-misaligned by text extraction and were reconstructed from the module's functional requirements rather than copied verbatim — each is flagged inline in the schema with `// reconstructed`.
   - **Not done, deliberately:** no migration was generated (`prisma migrate dev` needs a real Postgres connection this environment doesn't have) and per-field `@map()` snake-casing was not applied to the ~38 new models (only the original 4 infra models have it) — noted in-schema as a follow-up, not hidden.

**2. Eleven missing backend services given real module stubs.** `apps/api/src/{tenant,event,volunteer,contributor,contribution,payment,finance,document,notification,reporting,audit}/` now each have a controller + module following the exact pattern the existing `auth` module already established (one endpoint, honest `status: "skeleton"` response — not dressed up as more complete than it is), registered in `app.module.ts`. This was the single biggest gap this report identified (11 of 12 services had no code at all); it's still not business logic, but every service now has a real, buildable landing spot instead of nothing.

**3. A real, previously-undiscovered build bug found and documented (not fixed).** Type-checking `apps/api` directly (`tsc --noEmit -p apps/api/tsconfig.json`) fails with `TS6059: rootDir` errors on every import of a `@pauti-pustak/*` shared package — including the *pre-existing* `health`/`auth` modules, so this is not something introduced by the new modules (confirmed by re-running with `--rootDir` overridden, which compiles clean). Root cause: `tsconfig.base.json`'s path mapping lists each package's `src/index.ts` before its `dist/index.d.ts`, so TypeScript always resolves to source, and every app's `tsconfig.json` scopes `rootDir` to its own `./src`, which source from `packages/*` falls outside of. The same config is duplicated identically in `apps/worker` and `apps/scheduler`. This is left **unfixed** here: the standard fixes (TypeScript project references with `composite: true`, or restructuring `rootDir`/`outDir`) both change build output shape in ways that need verification against a real `pnpm`/`nx build` run, which this environment can't do (no working `pnpm`; `corepack enable` failed with an `EPERM` needing elevated permissions). Recommend fixing this before the next build-related task, with access to a working pnpm install to verify the fix.

**4. Mobile app-shell gap closed: `go_router` is now actually wired.** `apps/mobile/lib/app/router.dart` (new) defines a minimal `GoRouter` via a plain Riverpod `Provider` (not `@riverpod`/`riverpod_generator`, since codegen can't be run in this environment); `app.dart` now uses `MaterialApp.router` instead of a static `home:`. The former inline placeholder body moved to `lib/app/home_screen.dart`. This is intentionally minimal — one route — establishing the pattern correctly rather than building the full `(organizationId, eventId)` context-switch mechanism, which is real feature work deserving its own reviewed task, not something to bundle into a foundation pass.

**5. Other fixes applied:** the `intl` version conflict blocking `flutter pub get` (`^0.19.0` → `^0.20.2`, matching what `flutter_localizations` requires); a first widget test (`apps/mobile/test/app_test.dart`, zero → one, proving the test harness is reachable); the Helm chart's missing `Service` template (it had `values.yaml` fields for `service.type`/`port` with nothing consuming them); the README's tree diagram claiming an `infrastructure/docker/` folder that doesn't exist on disk.

**Still open, by design:** the TypeScript `rootDir` build bug (documented above, not fixed); Helm `Ingress` (still disabled by default in `values.yaml`, so left alone rather than inventing hostnames/TLS config); a proper `(organizationId, eventId)` tenant-context switching mechanism in the mobile app (real feature work); an actual Prisma migration (needs a live database); and the RBAC mismatch between `backend-security`'s hardcoded `UserRole` enum (`SUPER_ADMIN`/`ORGANIZATION_ADMIN`/`EVENT_MANAGER`/`FINANCE_OFFICER`/`VOLUNTEER`/`AUDITOR`) and the spec's per-organization custom-role model (`OrganizationRole`/`Permission`/`RolePermission`, with defaults Owner/President/Secretary/Treasurer/Donation Collector/Expense Approver/Auditor/Member) — discovered while modeling the schema, not resolved, since it's a real security-layer architecture decision that shouldn't be made unilaterally.

## Executive summary

The folder *shape* is good and largely complete: an Nx-managed pnpm monorepo with clean app/package separation, a Flutter app already wired for the right architectural ingredients (Riverpod, go_router, Drift, secure storage), a full observability/deployment stack (Helm, Kubernetes overlays, Grafana/Loki/Tempo/OTel), and a real, runnable CI pipeline. That's the good news, and it's genuinely more mature scaffolding than most projects have at this stage.

The bad news, and the single most important finding in this report: **almost none of it has business content yet.** The Prisma schema — the one artifact everything else ultimately depends on — defines exactly 4 models, and all 4 are generic infrastructure (health checks, idempotency, outbox, inbox). Not one of the ~15 domain models the backend spec requires (Organization, Event, Volunteer, ContributorAccount, ContributionBill, CollectionRecord, ContributionRecord, Receipt, ReceiptBook, Vendor, ExpenseApprovalPolicy, Expense, FinancialAccount, LedgerTransaction, AuditLog) exists anywhere. `apps/api` has 1 of 12 backend services represented (identity, as an explicit stub), and `apps/mobile`'s 16 feature folders were each a 2-line placeholder class with zero data/domain/presentation layers underneath — plus one file (`features.dart`) that wouldn't have compiled at all. This is a textbook case of **structure theater**: a monorepo that looks complete from `ls -R` but is close to empty by working-code measure. This is exactly the failure mode `MASTER-EXECUTION-GUIDE.md` warns about — *"A phase is not complete merely because files exist"* — and it's worth taking that warning literally here, not just as a slogan.

## Fixes applied this session (low-risk, additive only)

Given another process appears to be actively building this same scaffold concurrently, everything below was chosen to be small, obviously-correct, and non-conflicting — no domain modeling or architectural decisions were made on the backend side, since that's squarely the area most likely to collide with concurrent work.

1. **Fixed a real compile bug**: `apps/mobile/lib/features/features.dart` used `export const featureModules = [...]` — `export` cannot prefix a variable declaration in Dart; this file would have failed to build. Changed to a plain `const`.
2. **Fixed a `.gitignore` bug**: line 69 was `" scratch/"` with a leading space, which git treats as a literal (non-matching) pattern rather than ignoring a `scratch/` directory. Removed the stray space.
3. **Created the two asset directories** (`apps/mobile/assets/images/`, `apps/mobile/assets/icons/`) that `pubspec.yaml` already declares but which didn't exist on disk — a missing declared asset directory fails Flutter's build.
4. **Added 3 missing feature stub folders** to `apps/mobile/lib/features/`, matching the existing 16 folders' exact convention (one folder, one 2-line placeholder class, registered in `features.dart`): `receipt_books/`, `vendors/`, `expense_approval_policy/`. These three backend-spec epics had *no* representation at all, not even a stub — every other epic did.
5. **Updated `ERP-PLANNING/implementation-roadmap/TASK-BACKLOG.csv`**: marked the earlier `P0-001` (my now-discarded Melos multi-package Flutter workspace attempt) as `Superseded`, and logged this audit as `P0-002` with real evidence rather than a claimed-complete stub, per the framework's own evidence policy.

Nothing under `apps/api`, `apps/worker`, `apps/scheduler`, or `packages/backend-*` was modified — those are left exactly as found.

## The insights that matter most

**1. Tooling maturity and domain-code maturity are badly out of sync, and that's a leading indicator, not a cosmetic issue.** A team (or generation process) capable of producing a 5-stage CI pipeline, 3 Kubernetes overlays, and a full Grafana/Loki/Tempo observability stack is clearly capable of writing a Prisma schema — the fact that it hasn't yet suggests the scaffold was built top-down from an infrastructure template rather than bottom-up from the actual product. That ordering matters: infrastructure decisions (queue names, health-check shapes, observability pipelines) made before the domain model exists tend to need rework once real entities and their access patterns are known. Recommend modeling the Prisma schema *next*, before adding more infrastructure polish — it's the one artifact that everything else (API DTOs, worker payloads, mobile data layer) is currently blocked on.

**2. The apps/mobile dependency list already encodes real architectural commitments that aren't implemented yet — which is actually good news if caught now.** Riverpod + `riverpod_generator`, `go_router`, Drift + `sqlite3_flutter_libs`, `flutter_secure_storage`, and `connectivity_plus` are exactly the ingredients this session's own earlier architecture review recommended for tenant-context scoping, offline sync, and refresh-token handling. But `app.dart` doesn't use `go_router` yet, and there's no `ProviderScope`-based context-switching wired in. The risk: if real feature code starts landing in the 19 feature folders *before* the app-shell wiring (router, tenant-context scope, Drift schema, auth interceptor) is established, each feature will improvise its own pattern, and retrofitting consistency across 19 already-written features is far more expensive than establishing it once at the shell level first.

**3. Three backend-spec epics (Receipt Books, Vendors, Expense Approval Policy) were completely unrepresented until this session** — not stubbed, not folders, nothing. That's a real coverage gap in what otherwise looks like a deliberate 1:1 epic-to-folder mapping, and it's the same class of gap this session's earlier work already flagged independently (the redlined user-story doc added Receipt Books as its own epic for exactly the reason it's easy to silently drop: it has no independent navigation surface, so nobody notices its absence until someone goes looking for it, as happened here).

**4. There is very likely a second, concurrent process actively building this exact scaffold right now**, based on the sheer volume of new, consistent, spec-aligned material (full git repo, `node_modules` with 1337 resolved packages, generated Prisma client, a coherent 11-service docker-compose, a real CI pipeline) that appeared within this session's own working window, immediately after this session independently began planning the identical Phase 0 Foundation task from the same `ERP-PLANNING` prompts. If that's correct, the two highest-value near-term actions are: (a) confirm with whoever owns that other session before either side starts backend domain modeling, since duplicated Prisma schemas or NestJS module scaffolds would be expensive to reconcile later, and (b) treat this report, not a fresh restart, as the shared source of truth for "what's actually done" going forward — several of this scaffold's config files (README, Helm values) already describe capabilities (`infrastructure/docker/` subfolder, Ingress) that don't actually exist, which is worth correcting before it compounds.
